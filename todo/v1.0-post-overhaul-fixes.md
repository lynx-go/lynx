## P0 — 真 BUG（必须先修）

### 1. HTTP Stop 超时处理竞态，两个分支语义矛盾

**位置**：`server/http/server.go:292-313`（`Stop` 方法）。

**问题**：`hs.Shutdown(ctx)` 因超时返回 `context.DeadlineExceeded` 时，
`done` 关闭与 `ctx.Done()` 几乎同时就绪，`select` 随机选边：

- 选中 `done` 分支：`DeadlineExceeded`/`Canceled` 被第 300-303 行的过滤器
  当作"正常"放行——**返回 nil 且不做强制 Close**，未完成的连接被悄悄遗弃；
- 选中 `ctx.Done()` 分支：强制 `hs.Close()` 并返回超时错误。

同一事件两种矛盾结果。

**修法**：

- `done` 分支：`shutdownErr` 为 `DeadlineExceeded`/`Canceled` 时归入超时
  路径——强制 `hs.Close()`（记录 Close 错误日志）并返回
  `fmt.Errorf("http server graceful shutdown timed out: %w", shutdownErr)`；
  其他非 `http.ErrServerClosed` 错误保持现状（记日志并返回）。
- `ctx.Done()` 分支：先 `<-done` 等待 Shutdown 返回（ctx 已结束，它必然
  很快返回），再强制 Close 并返回超时错误。
- `ErrServerClosed` 仍视为正常（返回 nil）。

**验证**：新增回归测试——用一个永不结束的 handler + 极短
`ShutdownTimeout`，多次运行（`-count=20 -race`）断言 Stop **总是**返回
超时错误且连接被强制关闭，不出现返回 nil 的情况。

### 2. gRPC `reflection.Register` 放在 `Start` 中，二次 Start 必 panic

**位置**：`server/grpc/server.go:241`。

**问题**：gRPC 在 `Serve` 之后注册服务会 panic。框架当前不会重启服务
（latent bug），但一行改动即可根除。

**修法**：把 `reflection.Register(s.server)` 移到 `NewServer` 中
`grpc.NewServer` 创建之后、health 服务注册附近。

**验证**：现有测试全绿即可；如方便可加一个"NewServer 后反射服务已注册"
的断言。

## P1 — 契约一致性收尾

### 3. kafka / pubsub Router 的 `Start` 不尊重传入 ctx

**位置**：`contrib/kafka/transport.go:219-224`、`contrib/pubsub/router.go:41-44`。

**问题**：本轮重构已把 schedule/telemetry/memory 的 `Start` 改为阻塞在
**传入的** `ctx.Done()` 上，这两个仍阻塞在只有 `Stop` 能取消的内部 ctx
上，全库契约不一致；框架若调整中断顺序（先 cancel 后 Stop）会挂死。

**修法**（最小侵入，不破坏内部 goroutine 管理）：

- kafka `Start`：`select { case <-ctx.Done(): case <-t.ctx.Done(): }`——
  内部订阅/fan-in goroutine 对 `t.ctx` 的依赖保持不变；`Stop` 逻辑不动。
  running 标志的置位/复位不变。
- pubsub `Router.Start`：改为 `<-ctx.Done()`；若内部 ctx 仅服务于
  Start/Stop 信令，删除 `r.ctx/r.cancel`，`Stop` 变为直接返回 nil
  （仍须容忍 Stop-before-Start，自然是满足的）；若内部 ctx 还有其他
  使用者，则与 kafka 同样用 select 双监听。

**验证**：两个包的现有测试（含 stop-before-start、竞态测试）全绿；
为 kafka 补一个"Start 的 ctx 被直接取消时 Start 返回"的用例。

### 4. gRPC option 命名与 HTTP 对齐

**位置**：`server/grpc/server.go:89`（`WithHealthCheck`） vs
`server/http`（`WithHealthCheckers`）。

**修法**：gRPC 侧改名 `WithHealthCheckers`（两者均接受
`lynx.HealthCheckersFunc`，未发版可直接改）。同步更新
`docs/05-servers.md`、`_examples` 中的调用点。

### 5. pubsub `Router.Init` 的 nil 防御只做了一半

**位置**：`contrib/pubsub/router.go:26-37`。

**问题**：`if ctx != nil { r.logger = ... }` 只保护了 logger 赋值，
第 31、37 行的 `ctx.Context()` 对 nil `AppContext` 直接 panic。
这个半截 guard 造成"容忍 nil"的错觉（command/schedule 都整体容忍
nil，供脱离框架单用）。框架永远传非 nil，属 standalone 场景的
latent panic。

**修法**：对齐 command/schedule 风格整体容忍 nil——logger 已在
`NewRouter` 中回落 `slog.Default()`，把 `ctx.Context()` 的取值抽为
带 fallback（`context.Background()`）的局部变量；或者反过来，删掉
guard 并在 `NewRouter` 注释明确"Init 要求非 nil AppContext"。推荐前者。

**验证**：补一个 `r.Init(nil)` 不 panic 的用例（如选前者）。
