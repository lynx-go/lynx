## P0 — 发布阻断项（必修）

### P0-1 gRPC health 轮询缺省值 panic（实测崩进程）

- 位置：`server/grpc/server.go:29`（`DefaultHealthCheckPeriod=10s` 定义后从未被引用）、`:128-132`（NewServer 缺省值装配）、`:251`（`time.NewTicker(0)`）。
- 证据：`NewServer(WithHealthCheck(...))` 不设 Period 时 Period 为零值，轮询 goroutine 内 `time.NewTicker(0)` panic，进程崩溃。临时测试已实测复现。
- 修复方案：NewServer 中对零值/负值 Period 回退 `DefaultHealthCheckPeriod`；或在 WithHealthCheck 选项应用后统一 sanitize。倾向前者，与框架其他缺省值处理一致。
- 验收：`go test -race ./server/grpc/...` 新增用例"缺省 Period 不 panic 且按 10s 轮询"通过。
- [x] 已修复 @server/grpc/server.go + server_test.go: NewServer 对零值/负值 Period 回退 DefaultHealthCheckPeriod；新增 TestHealthCheckDefaultPeriodNotPanic 走真实 Start/Stop 验证无 panic。

### P0-2 Kafka SCRAM 声明支持但 100% 报错

- 位置：`contrib/kafka/transport.go:347-350`（接受 SCRAM-SHA-256/512 但从不设置 `SCRAMClientGeneratorFunc`）。
- 证据：sarama v1.43.3 `config.go:655` 在 `Validate()` 强制要求 SCRAMClientGeneratorFunc；实测 SCRAM 配置下 Publish 先于网络连接报 `invalid configuration`。现有 `TestSASLTLSConfigMapping` 走 fake seam 绕过校验，故未暴露。
- 修复方案（二选一，倾向 a）：
  a. 实现 SCRAM 支持：按 sarama 示例注入 `XDGSCRAMClient` 生成器（SHA-256/512 分派），并补真实 sarama.Config 校验路径的测试（不经 fake seam）；
  b. v1.0 显式拒绝：配置校验阶段对 SCRAM mechanism 返回明确错误"SCRAM 将于 v1.1 支持"，并更新文档。
- 验收：SCRAM 配置要么能过 sarama `Validate()`（真实路径测试），要么报清晰的"不支持"错误；测试不得走 fake seam。
- [x] 已修复 @contrib/kafka/scram.go + transport.go + transport_internal_test.go: 按 sarama 示例注入 XDGSCRAMClient 生成器（SHA-256/512 分派）；新增 TestSCRAMConfigPassesSaramaValidate（真实 cfg.Validate() 路径，不经 fake seam）与 TestXDGSCRAMClientHandshake（与 xdg-go/scram 服务端跑完整挑战-应答）；新增直接依赖 github.com/xdg-go/scram v1.2.0（API 冻结例外：SCRAM 支持的必要实现依赖）。

### P0-3 schedule "免 Init 直接 Start"路径挂死窗口

- 位置：`contrib/schedule/scheduler.go:99-118`（Start/ensureBackgroundCtx）、`:137,:144`（Stop 提前返回分支）。
- 证据：交错序列——Start 过 :100 检查 → Stop 读到 `cancel==nil` 且 `started==false` 提前返回 → Start 经 :108 建 Background 衍生 ctx 后在 :118 永无人取消，挂死。压力测试 20000 次命中 1 次。框架内不可达（lynx.go 保证 Init 先于 Start），但 `ensureBackgroundCtx` 注释明确承诺支持免 Init 用法。
- 修复方案：Start 在 :115 持锁复查分支中，若发现 `stopping` 已置位则 `s.cancel()` 后直接返回错误（或返回约定错误），不得进入阻塞。同步检查 `scheduler.ctx` 读侧（:241）与 ensureCtx 写侧的 mu 保护注释是否属实。
- 验收：新增并发交错测试（Stop 抢在 ensureCtx 前后）10 万次无挂死；`go test -race` 通过。
- [x] 已修复 @contrib/schedule/scheduler.go + scheduler_test.go: Start 复查分支发现 stopping 已置位时 cancel 刚创建的 ctx 并直接返回错误（不再进入无人取消的阻塞）；新增 TestStopRacingStartNoHang 10 万次交错测试。附带核验：:241 处 scheduler.ctx 读侧仅发生在 cron 派发之后（cron 内部 channel 同步保证 Start 写先行），mu 保护注释属实。

## P1 — Major（v1.0 前须定语义，能修则修）

### P1-1 Register 与 Run 并发为未定义行为且存在 data race

- 位置：`lynx.go:378`（Register 侧持 `app.mu` 调 `runG.Add`）vs `lynx.go:461`（Run 侧不持锁遍历/运行 actors）；`command.go:91` 注释声称等待 Start 后注册的组件。
- 证据：-race 实测 DATA RACE（oklog/run group.go:22）；Run 后注册的组件永不 Start（actors 已快照）却计入 `components`/`healthCheckers`、关停时被 Stop，Command 会苦等其健康至 MaxTries 耗尽。
- 修复方案（倾向 b）：
  a. 支持运行时注册：Run 侧持锁或改用并发安全 group——改动大，不建议 v1.0 做；
  b. 定语义为禁止：Run 开始后 `Register`/`RegisterBuilders` 立即返回错误（或 panic，与框架 Fatal 风格一致），在 App 接口注释、CLAUDE.md:98、command.go:91 写明"所有注册必须先于 Run"；command.go:91 矛盾注释同步修正。
- 验收：新增测试"Run 后 Register 报明确错误"；-race 通过；三处文档一致。
- [x] 已修复 @lynx.go + command.go + CLAUDE.md: 按方案 b 定语义——Run 开始后 Register/RegisterBuilders panic 报明确错误（Register 无返回值，panic 与框架 Fatal 风格一致）、CLI 返回错误；App 接口 GoDoc、CLAUDE.md:98、command.go:91 三处文档统一为"所有注册必须先于 Run"；新增 TestRegisterAfterRunRejected。

### P1-2 OnStop 错误可被 oklog/run 语义吞掉

- 位置：`lynx.go:461-469`（shutdown actor）、`:496-530`（ShutdownErrors 聚合）。
- 证据：组件 Start 先失败时，OnStop 钩子在 interrupt 路径执行了，但 Run() 只返回第一个 actor 的错误，实测 `Run()="start boom"`，`onstop boom` 仅落日志。
- 修复方案：Run 返回前将 shutdownErr 与 oklog/run 返回值用 `errors.Join` 聚合（nil 安全），或在文档明确"组件错误优先、OnStop 错误仅记录日志"。倾向聚合——与 v1.0 "OnStop 错误上抛"的承诺一致。
- 验收：新增测试"组件 Start 失败 + OnStop 失败时 Run() 返回包含两者"。
- [x] 已修复 @lynx.go: 关闭 actor 改为返回 nil，Run 末尾 `errors.Join(runG.Run(), shutdownErr)` 聚合（nil 安全、无重复）；新增 TestRunJoinsOnStopErrorsWithStartFailure。
