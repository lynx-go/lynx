# Lynx 全量架构与代码审查（2026-08-25）

> 审查范围：全部 121 个 Go 文件（核心包、eventbus、server/、client/、boot/、logging/、debug/、7 个 contrib 模块）、设计文档、CI 配置。
> 审查基线 commit：`3d89fea`（master）。审查时 `go vet` 0 问题，主模块 `go test -race` 全部通过。
> 本文档同时作为修复跟踪清单：状态列 ☐=未修复，✅=已修复（复审通过），⚠️=已修复待复审，➖=不修（附理由）。

## 结论摘要

整体设计成熟度高于平均水准：生命周期模型严谨（锁外 Init、事务化登记、有界关停、排水窗口）、EventBus 三件套抽象小而准、注册发现五件套职责单一、回归测试体系罕见地严谨。存在 2 个 Critical 正确性缺陷（其一默认触发）、约 10 个 High 级生产隐患，集中在：Kafka 消费组语义冲突、毒消息无限重投、健康检查无界、关停竞态、错误信息泄露、zap 默认采样丢日志。

架构级结论（修复时保持的方向）：

1. 内存 Bus 与 Kafka Bus 投递语义是两个极端（内存=缓冲满丢弃/重试耗尽丢弃；Kafka=无限重投），必须文档化并对齐逃生机制。
2. `CheckHealth() error` 无 ctx/超时/缓存是接口级缺陷，修复在调用侧包装（保持接口兼容）。
3. `WithTimeout` 在 HTTP/gRPC 两侧语义相反，需加别名并对齐文档。
4. 框架把一切 `Start` 错误发布为 `lynx.service.failed`，server 侧需归一化关停错误。
5. Resolver 缺订阅 API 导致 gRPC 只能 5s 轮询（本次仅做超时防护与文档，订阅 API 列为后续工作）。
